# Comments

판정 기준은 하나 - **지우면 다음 사람이 사고를 내는 주석인가.** 아니라면 삭제할 것.

주석에는 코드에서 추론할 수 없는 것만 적음. 비즈니스 규칙, 외부 시스템과의 계약,
라이브러리 우회 사유, "이 코드를 지우면 안 되는 이유"가 여기에 해당함. 길이 제한은 없음.
좋은 주석은 길어도 값을 하고, 나쁜 주석은 한 줄이어도 거짓말이 되기 때문임.

## 주석 작성 필수 요건

시그니처(이름·파라미터·반환·throws)만 읽어서는 알 수 없는 계약이 하나라도 있으면 주석
의무. 반대로 시그니처만으로 전부 추론되는 것(단순 조회, 위임 한 줄)은 public 이어도
강제하지 않음. 강제하면 아래에서 금지하는 "코드 낭독" 주석을 양산하게 됨.

| 기준 | 예시 |
|---|---|
| 숨은 부작용: 이름에 드러나지 않는 상태 변경·I/O·외부 시스템 호출이 있음 | 큐 reader 클래스 javadoc 이 "헤더의 적재 완료 위치를 이 클래스로 읽고 씀"을 밝힘. reader 가 쓰기도 한다는 사실은 이름만으로 추론할 수 없음 |
| 호출 계약: 호출 순서 전제, 선행 조건, null/빈 값의 특별한 의미가 있음 | 같은 클래스의 헤더 쓰기 메서드 javadoc 이 "DB 적재 성공 후에만 쓸 것"이라는 선행 조건을 밝힘 |
| 동시성·복원력: 락, 재시도, 멱등성, 크래시나 짧은 I/O 뒤에도 안전한 이유가 있음 | 같은 메서드의 "찢어져도 0 으로 되돌려 다시 적용하면 되므로(멱등) 원자성 논증 불필요". 이 주석이 없으면 다음 사람이 찢어진 헤더를 버그로 보고 원자적 쓰기를 덧붙이게 됨. 사전 잔량 확인 메서드의 "동시 요청 경쟁 탓에 100% 방지는 아니며 최종 차감에서 다시 확인함"도 같은 갈래이며, 없으면 다음 사람이 중복 검사로 보고 삭제하게 됨 |

## 흐름 메서드의 단계 주석

여러 하위 단계를 정해진 순서로 이어 붙이는 흐름 메서드(엔진·오케스트레이션 성격으로,
단계 순서 자체가 계약인 경우)는 본문을 번호 단계 주석(`// 1.`, `// 2.`)과 단계 사이
빈 줄로 분리할 것. javadoc 의 순서 선언을 본문 구조로 되비추는 것이라 코드 낭독이 아님.

- 단계 라벨은 "무엇"을 한 구절로 짧게 쓰고, 근거("왜")는 위 요건대로 해당 단계 아래에 둘 것.
- 라벨 표기는 번호로 통일함. `[읽기]` 같은 괄호 라벨 금지.
- 단순 조회·위임 수준의 짧은 메서드에는 강제하지 않음. 강제하면 코드 낭독을 양산하게 됨.
- 예시: 큐 소비 엔진의 runOnce / processBatch / dispatch / commit 처럼 여러 단계를 순서대로 잇는 메서드

## 금지

| 금지 | 예시 |
|---|---|
| **미해결 과제를 코드에 남기기. 예외 없음.** "조사 필요", "범위 밖", "후속" 같은 내용은 태스크 파일로 옮길 것 | Repository 클래스 javadoc 에 "취소 건 처리는 추후 조사" 같은 미해결 메모가 남으면, 아무도 보지 않은 채 코드와 함께 굳음 |
| 코드 낭독. 메서드명·시그니처·throws 로 드러나는 것을 문장으로 옮기지 말 것 | `deduct(amount)` 의 javadoc 이 "amount 만큼 차감한다, 부족하면 예외를 던진다" 처럼 이름·파라미터·throws 를 되뇌면 정보량이 0임 |
| 태스크 이력 누적. "지금 참인 규칙"만 남길 것. 이력은 git 이 보관함 | 4줄짜리 record 에 태스크별 변경 문단이 쌓여 주석이 코드보다 길어짐 |
| 남의 동작 서술. 자기 파일이 하지 않는 일을 설명하지 말 것 | 검색 조건 DTO 주석이 repository 의 정렬·AND 결합 규칙을 서술하면, 그 코드가 바뀔 때 주석은 조용히 거짓말이 됨 |

## 유지보수

- `@param` 은 이름이 담지 못하는 제약(단위, 범위, null 의 의미)이 있을 때만 적을 것.
- 규칙이 바뀌면 문단을 추가하지 말고 기존 문장을 고쳐 쓸 것. 태스크 ID 는 근거 추적용으로 규칙당 최신 1개만 남길 것.
- 한 줄 주석으로 설명해야 하는 변수·메서드는 주석을 다는 대신 이름을 고칠 것.

## 문체

주석은 개조식으로 작성함. 명사형 또는 `~음` / `~함` / `~됨` 으로 끝맺고, 지시는
`~할 것` / `~금지` 로 씀. 서술형 `~한다`와 해요체는 주석에서 금지함.

## 형식

사람이 위에서 아래로 한 번 읽고 바로 쓸 수 있게 구성함.

- 한 줄이나 한 항목에는 주제 하나만 담을 것. 다른 주제를 마침표로 이어 붙이지 말고 줄을 나눌 것
- 한 주제를 설명하는 데 여러 문장이 필요하면 축약하지 말고 풀어 쓸 것
- 명령은 복사해 바로 실행할 수 있게 한 줄에 온전히 적을 것
- 파일 머리 주석이 여러 항목이면 정형화할 것
  - 첫 줄: 이 파일이 무엇인지 한 문장
  - 사용법: `<동작>: <명령 또는 값>` 줄을 쓰는 순서대로 둠
  - 주의: `주의` 머리 아래 `- ` 목록으로 둠
- 항목 사이는 빈 주석 줄(`#`)로 나눌 것

## 언제 언어별로 쪼갤 것인가

현재는 한 파일로 유지함. 금지 규칙 넷이 Java 와 셸에서 같은 모양으로 나왔고 언어 특정
내용은 `@param` 한 줄뿐이라, 지금 쪼개면 껍데기 파일만 늘어남. 언어 고유의 함정이
실제로 관측되면 그때 `comment/` 디렉터리로 옮겨 `common.md` + `java.md` + `shell.md` 로
분리함.
